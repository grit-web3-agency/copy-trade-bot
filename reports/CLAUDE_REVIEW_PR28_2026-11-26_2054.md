Review of sprint-5 payment adapter PR.

I read the code on the current checkout (`dev/auto-continue-20261126-1525`) and did not run the tests or modify anything. If the PR branch differs from this checkout, line references may be off.

## 1) Summary

The compatibility shims work for the mock path, but the PR leaves two parallel adapter systems and, more importantly, never verifies a payment before activating a subscription. I recommend consolidating rather than keeping the shims, and not merging until changes 1–3 below land.

- **Two adapter systems:** `src/payment.ts` selects by `PAYMENT_MODE` and uses `src/payments/stripeMock.ts`. `src/payments/index.ts` selects by `PAYMENT_PROVIDER` and uses `providers/mock.ts` and `providers/stripe-mock.ts`. Only the first is used by `bot.ts` and the webhook; the second is only reached from `tests/payment-adapter.test.ts`.
- **No verification:** `/subscribe` (`src/bot.ts:443`) calls `activateSubscription` directly. `verifyPayment` is only ever called from tests, so `/subscribe pro anything` grants Pro.
- **`ENABLE_PAYMENTS` is not enforced:** `isPaymentsEnabled()` is never called from production code, so the "disabled by default" note in the PR is not true in practice.

## 2) Prioritized changes

1. **Verify before activating** — `src/payment.ts`, `activateSubscription`. For paid plans, require a signature and a passing verification:
```ts
const plan = service.PLANS[planId];
if (plan.priceSolMonthly > 0) {
  if (!txSignature) return false;
  if (!(await verifyPayment(txSignature, plan.priceSolMonthly, getTreasuryAddress()))) return false;
}
```

2. **Fail closed** — `src/payment.ts:79` and `selectAdapter`.
- Replace the final `return true` in `verifyPayment` with `return false`.
- Make `PAYMENT_MODE=stripe` throw "not implemented" instead of silently returning `StripeMock`.
- Refuse a mock adapter when `NODE_ENV=production`.

3. **Block signature replay** — `src/payments/service.ts`. Nothing stops one signature being reused across users or renewals. Add a unique index and wrap `createSubscription`'s UPDATE and INSERT in `database.transaction(...)`:
```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_sub_tx ON subscriptions(tx_signature) WHERE tx_signature IS NOT NULL;
```

4. **Enforce `ENABLE_PAYMENTS`** — `src/bot.ts` (`/subscribe`) and `src/api/payments/webhook.ts`. Gate both on `isPaymentsEnabled()` and reply "payments disabled" otherwise.

5. **Consolidate the adapter shape** — `src/payments/adapter.ts`. Use one required method and delete the legacy/new split:
```ts
export interface PaymentAdapter {
  verifyPayment(req: { txSignature: string; expectedSol: number; treasury: string; connection?: Connection }): Promise<PaymentVerification>;
  verifyWebhookPayload?(payload: unknown): Promise<PaymentVerification>;
}
```
Move activation out of the adapter into `service.ts`, since it is a database write and not provider-specific.

6. **Update providers and remove shims** — this depends on change 5.
- Port `providers/mock.ts` and `providers/stripe-mock.ts` to the new signature.
- Delete `src/payments/stripeMock.ts`.
- Have `src/payment.ts` use `getPaymentAdapter()` and drop every `(adapter as any)` cast.
- Pick one env var: keep `PAYMENT_MODE` (already validated in `src/env-validation.ts`) and drop `PAYMENT_PROVIDER`.
- The current legacy shim also passes the treasury wallet into the `payerPubkey` parameter, which this removes.

7. **Remove dead result handling** — `src/bot.ts:445-447` and `src/api/payments/webhook.ts:86-88`. `activateSubscription` returns `Promise<boolean>`, so the "boolean or object" branches never run. Either drop them or return `{ success, error }` so users see a real failure reason instead of "unknown error".

8. **Fix `checkDailyTradeLimit`** — `src/payment.ts:46`. It returns `limit > 0` without counting trades, so it always allows, and it is only called from `scripts/e2e-payment-demo.ts`. Add a `tradesToday` parameter, return `tradesToday < limit`, and call it from the trade execution path.

9. **Authenticate the webhook** — `src/api/payments/webhook.ts`. `handlePaymentWebhook` trusts the payload and never calls `verifyWebhookPayload`. Add a shared-secret or HMAC check and make it idempotent on `tx_signature`. I did not check how this handler is exposed over HTTP, so confirm whether it is reachable.

10. **Add CI** — there is no `.github/workflows/` directory. Add `ci.yml` running `npm ci && npx tsc --noEmit && npm test`, and add `"e2e:payment": "tsx scripts/e2e-payment-demo.ts"` to `package.json`.

11. **Shrink the PR** — the branch is about 1,050 commits ahead of `main`, with 55 files changed under `src/` and `tests/`. Move the sprint reports and `drafts/telegram_*` files out, and squash the `chore(reminder)` commits so the payment change is reviewable.

## 3) Risks and tests to add

**Risks**
- **Free upgrades:** in the current state any user can get a paid plan with a made-up signature.
- **Stricter mocks break tests:** after change 6, `providers/stripe-mock` only accepts signatures starting with `stripe-`, so tests using `sig-activate-1` or `mock-tx-sig-001` will need updating.
- **Unique index migration:** the index in change 3 will fail to create on a database that already has duplicate signatures; dedupe first.
- **"241 passed" is weak evidence:** the tests exercise always-true mocks, so they would pass with verification missing.

**Tests to add**
- Paid plan with no signature is rejected.
- A failed verification creates no subscription row.
- A reused signature is rejected, for the same user and for a different user.
- An adapter with no verify method returns false.
- `PAYMENT_MODE=stripe` throws until a real adapter exists.
- `ENABLE_PAYMENTS=false` blocks both `/subscribe` and the webhook.
- A webhook with a bad signature is rejected, and a duplicate webhook is a no-op.
- `checkDailyTradeLimit` at limit−1, at the limit, and for an expired subscription falling back to Free.
- One contract test suite run against every provider.
